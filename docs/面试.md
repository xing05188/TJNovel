## 一、项目概述与背景

### Q1: 请简单介绍一下这个项目，它的定位和目标是什么？

**参考回答：**

TJNovel 是一个全栈微服务架构的小说阅读与管理平台，定位是提供一个功能完整、可独立部署的小说平台解决方案。项目覆盖了小说平台的核心业务链路：

- **读者端**：小说浏览、搜索、阅读、收藏、评论、评分、充值打赏、购买
- **作者端**：小说创建发布、章节管理、收入统计、读者互动
- **管理员端**：内容审核、用户管理、举报处理、数据统计

技术选型上，我们采用了 Java 17 + Spring Boot 3.3.5 + Spring Cloud 2023.0.3 构建后端微服务集群，Vue 3 + Element Plus 构建前端 SPA 应用，并集成了 Redis、RabbitMQ、Elasticsearch、MinIO 等中间件，通过 Docker Compose 实现一键部署。

### Q2: 为什么要采用微服务架构？单体架构是否也能满足需求？

**参考回答：**

选择微服务架构主要基于以下几点考虑：

1. **业务复杂度**：平台涉及用户、内容、交易、管理、通知等多个业务域，彼此之间逻辑耦合度低，天然适合拆分。
2. **独立扩展性**：不同服务的负载特征差异大——内容服务读多写少（小说阅读），交易服务对一致性要求高，通知服务处理异步消息。拆分后可按需独立扩缩容。
3. **团队协作**：微服务架构允许不同团队并行开发不同服务，减少代码冲突和发布耦合。
4. **技术异构灵活性**：各服务可根据自身需求选择合适的技术栈（虽然目前统一使用 Spring Boot，但未来某服务可独立升级版本或替换框架）。

**单体架构的局限性**：初期确实可以用单体快速验证，但随业务增长，单体应用会面临代码膨胀、构建缓慢、局部故障影响全局等问题。我们从项目启动时就设计了微服务架构，避免了后期重构的高昂成本。

### Q3: 项目中有 5 个业务微服务（外加 Gateway 统一入口），它们之间的通信方式是什么？如何保证数据一致性？

**参考回答：**

服务间通信采用两种方式：

1. **同步通信（RESTful API）**：通过 Spring Cloud Gateway 统一路由，服务间通过 HTTP 调用。例如 content-service 需要验证用户身份时，通过 Gateway 路由到 user-service 的认证接口。
2. **异步通信（RabbitMQ）**：对于不需要实时响应的场景，如小说更新通知、订单回调、审核结果推送等，使用 RabbitMQ 进行异步消息传递。

**数据一致性策略**：
- **最终一致性**：通过 RabbitMQ 消息队列实现。例如用户充值后，transaction-service 发布充值成功事件，notification-service 消费后发送通知。如果消费失败，消息会进入死信队列，通过重试机制保证最终送达。
- **分布式锁**：针对防重复充值、防重复打赏等场景，使用 Redisson 分布式锁保证同一时间只有一个请求能处理。
- **本地事务 + 消息表**：对于关键业务（如支付），采用本地事务写入业务数据和消息表，再由后台任务轮询发送消息，确保事务与消息的原子性。

## 二、微服务架构设计

### Q4: 5 个业务微服务的拆分依据是什么？每个服务的职责边界如何划分？

**参考回答：**

拆分遵循"高内聚、低耦合"和"领域驱动设计（DDD）"的思想，按业务领域划分：

| 服务 | 核心职责 | 拆分理由 |
|------|---------|---------|
| **api-gateway** | 统一入口、路由转发、CORS、请求过滤 | 关注点分离，将网关逻辑与业务逻辑解耦 |
| **user-service** | 注册登录、JWT 认证、个人信息、头像管理 | 用户身份是全局基础服务，独立出来便于复用 |
| **content-service** | 小说/章节 CRUD、分类、收藏、评论、搜索 | 内容数据量最大、访问最频繁，需独立扩展 |
| **transaction-service** | 充值、打赏、购买、作者收入 | 交易涉及资金安全，需要严格的事务保障 |
| **admin-service** | 审核管理、用户管理、举报处理 | 管理后台权限要求高，与普通用户接口隔离 |
| **notification-service** | 消息通知、异步事件处理 | 通知逻辑可异步处理，不影响主业务流程 |

> **注**：上表中的 api-gateway 是统一入口 / 边缘服务，不属于业务微服务；真正按业务域拆分的微服务为用户、内容、交易、管理、通知共 5 个。

### Q5: 服务之间如何实现服务发现和负载均衡？为什么没有使用 Nacos 或 Eureka？

**参考回答：**

当前项目通过 Docker Compose 的 DNS 解析实现服务发现——Docker 内部网络中，容器名即主机名，服务之间通过 `http://user-service:7081` 直接访问。API Gateway 中配置了各服务的地址映射：

```yaml
services:
  user: ${SERVICES_USER:http://localhost:7081}
  content: ${SERVICES_CONTENT:http://localhost:7082}
```

**为什么没有使用注册中心**：
- 项目当前为单体部署模式（所有服务运行在同一 Docker 环境中），Docker 内置 DNS 解析足够满足需求。
- 引入 Nacos/Eureka 会增加运维复杂度，对于当前规模收益不大。
- 未来如果扩展到多节点部署（同一服务多实例），会引入 Spring Cloud LoadBalancer + 注册中心来实现负载均衡。

### Q6: 如果某一个微服务挂掉了，如何保证系统整体可用性？有没有做熔断降级？

**参考回答：**

目前项目主要通过以下方式保证可用性：

1. **Docker 健康检查 + 自动重启**：docker-compose.yml 中为每个服务配置了 healthcheck，并设置 `restart: unless-stopped`，服务异常退出后 Docker 会自动重启。
2. **Gateway 层面的容错**：Gateway 路由到下游服务时，如果某个服务不可用，会返回 503 状态码，前端可进行相应的降级提示。
3. **异步解耦**：关键业务使用 RabbitMQ 异步处理，消息生产方不依赖消费方的可用性。例如发布小说时，内容服务只需写入数据库并发送消息，后续的搜索索引更新、通知推送等由消费方异步处理。

**未来可改进**：引入 Resilience4j 实现断路器（Circuit Breaker）和限流（Rate Limiter），当某个服务故障率达到阈值时自动熔断，避免级联故障。

## 三、Spring Cloud Gateway 与 API 网关

### Q7: 为什么选择 Spring Cloud Gateway 而不是 Zuul 或 Nginx？

**参考回答：**

1. **Spring Cloud Gateway 基于 WebFlux（Reactive）**，底层使用 Netty，非阻塞 I/O 模型，性能优于 Zuul 1.x（基于 Servlet，阻塞式 I/O）。
2. **与 Spring Cloud 生态深度集成**：可以无缝使用 Spring Security、配置中心、服务发现等组件。
3. **路由配置灵活**：支持通过 Java DSL 或 YAML 配置路由规则，支持断言（Predicate）和过滤器（Filter）的链式组合。
4. **Nginx 的定位不同**：Nginx 是反向代理和负载均衡器，适合做流量入口层的转发。Spring Cloud Gateway 更适合做应用层的网关，可以进行更细粒度的请求处理（如鉴权、限流、日志等）。生产环境通常将两者结合使用：Nginx 做第一层负载均衡，Spring Cloud Gateway 做第二层应用网关。

### Q8: Gateway 中如何处理跨域请求（CORS）？

**参考回答：**

在 api-gateway 中配置了全局 CORS 策略：

```java
@Bean
public CorsWebFilter corsWebFilter() {
    CorsConfiguration config = new CorsConfiguration();
    config.addAllowedOrigin("http://localhost:8080"); // 前端地址
    config.addAllowedMethod("*");
    config.addAllowedHeader("*");
    config.setAllowCredentials(true);

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return new CorsWebFilter(source);
}
```

关键点：
- 使用 `CorsWebFilter`（WebFlux 版本）而非 `CorsFilter`（Servlet 版本）
- `allowCredentials(true)` 必须与具体 `allowedOrigin` 配合，不能使用 `*`
- 前端所有请求先经过 Gateway，再由 Gateway 路由到各微服务，所以只在 Gateway 层配置 CORS 即可，各微服务不再需要配置

### Q9: Gateway 的路由规则是如何设计的？

**参考回答：**

Gateway 根据请求路径的前缀将请求路由到对应的微服务。例如：

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: user-service
          uri: ${SERVICES_USER:http://localhost:7081}
          predicates:
            - Path=/api/user/**
        - id: content-service
          uri: ${SERVICES_CONTENT:http://localhost:7082}
          predicates:
            - Path=/api/content/**
```

前端所有 API 请求都发往 Gateway 的 7080 端口，Gateway 根据路径前缀自动转发。这样做的好处是前端只需要知道一个入口地址，后端服务变更对前端透明。

## 四、MyBatis-Plus 与数据库

### Q10: 项目中同时使用了 JPA 和 MyBatis-Plus，为什么这样设计？两者如何分工？

**参考回答：**

项目以 **MyBatis-Plus 为主**，JPA 为辅：

- **MyBatis-Plus**：负责核心业务逻辑的数据库操作，如复杂查询、分页、批量操作等，利用其条件构造器（LambdaQueryWrapper）和分页插件大幅减少 SQL 编写量。
- **JPA**：主要用于一些简单的 CRUD 操作和表结构自动生成（通过 `ddl-auto` 机制）。

**实际使用中**：JPA 更多是项目早期遗留的依赖，核心业务代码已逐步迁移到 MyBatis-Plus。如果重新设计，会直接统一使用 MyBatis-Plus，减少维护两套 ORM 的成本。

### Q11: MyBatis-Plus 相比原生 MyBatis 有哪些优势？项目中具体用到了哪些特性？

**参考回答：**

MyBatis-Plus 的优势与使用场景：

| 特性 | 使用场景 |
|------|---------|
| **BaseMapper 内置 CRUD** | 90% 的单表操作无需编写 XML，直接调用 `insert`、`selectById`、`updateById` 等方法 |
| **LambdaQueryWrapper** | 动态条件查询，如按小说分类、状态、关键词组合筛选，类型安全，避免 SQL 注入 |
| **分页插件（PaginationInnerInterceptor）** | 小说列表、评论列表、排行榜等分页查询，只需传入 `Page` 对象即可 |
| **乐观锁插件（OptimisticLockerInnerInterceptor）** | 作者收入更新等并发场景，防止脏写 |
| **逻辑删除** | 评论、小说等内容的软删除，保留数据可追溯 |
| **代码生成器** | 快速生成 Entity、Mapper、Service 层代码，提高开发效率 |

### Q12: 数据库表结构是如何设计的？分库的依据是什么？

**参考回答：**

项目采用**按微服务拆分数据库**的策略，每个微服务使用独立的数据库：

- `userdb`：用户表、角色表、权限表
- `contentdb`：小说表、章节表、分类表、评论表、收藏表、评分表等
- `transactiondb`：充值记录表、打赏记录表、购买记录表、作者收入表
- `admindb`：管理日志表、审核记录表

**分库的依据**：
1. **数据隔离**：不同业务域的数据互不干扰，某个数据库出问题不会影响其他服务。
2. **独立扩展**：内容服务的数据量最大，未来可以独立对 contentdb 做读写分离或分库分表。
3. **安全权限**：交易数据库的访问权限最严格，与用户库、内容库分离便于权限管控。

## 五、Redis 缓存与分布式锁

### Q13: Redis 在项目中承担了哪些角色？缓存策略是怎样的？

**参考回答：**

Redis 在项目中主要承担以下角色：

1. **热点数据缓存**：缓存热门小说信息、章节内容，减少数据库查询压力。缓存策略如下：
   - **缓存穿透防护**：查询不到数据时，缓存空值（较短过期时间，如 60 秒）
   - **缓存雪崩防护**：缓存过期时间添加随机值（基础时间 ± 随机范围），避免大量缓存同时过期
   - **缓存更新策略**：采用"先更新数据库，再删除缓存"的模式（Cache-Aside Pattern）

2. **分布式锁**：使用 Redisson 的 `RLock` 实现，防止重复充值、重复打赏等操作。

3. **排行榜（ZSet）**：使用 Redis 有序集合实现小说阅读排行榜、热销榜等，支持按分数排序和范围查询。

4. **Session 共享**：用户登录状态存储在 Redis 中，各微服务共享 Session 数据。

### Q14: Redisson 分布式锁的实现原理？如何避免死锁？

**参考回答：**

Redisson 分布式锁基于 Redis 的 SETNX + Lua 脚本实现，核心机制：

1. **加锁**：使用 Lua 脚本原子性地执行 `SETNX key value` 和设置过期时间。
2. **看门狗（WatchDog）机制**：默认锁的超时时间为 30 秒，Redisson 会启动一个后台定时任务，每隔 10 秒检查一次锁是否还在持有，如果还在则续期 30 秒。这避免了业务执行时间超过锁超时时间导致锁提前释放的问题。
3. **解锁**：使用 Lua 脚本原子性地验证锁持有者 → 删除锁。

**避免死锁的措施**：
- 每个锁都有过期时间，即使客户端崩溃，锁也会自动释放。
- 解锁时校验锁的持有者（通过 UUID + 线程 ID 标识），防止误删其他客户端的锁。
- 看门狗机制确保业务未完成时锁不会提前过期。

**锁的 Key 设计与事务边界（以「防重复充值 / 打赏」为例）**：
- **Key 设计**：`lock:recharge:{userId}:{orderNo}`（打赏为 `lock:reward:{userId}:{orderNo}`），以「用户 ID + 业务单号」保证同一用户对同一笔订单同一时刻仅一个请求能获取锁，不同用户 / 不同订单互不阻塞。
- **获取与释放**：业务逻辑开始前 `tryLock`，数据库事务 `commit` 成功之后再 `unlock`；获取锁失败直接返回「操作进行中」，避免重复提交。
- **异常兜底**：业务抛异常时也在 `finally` 中释放锁，配合看门狗避免死锁。

### Q15: 如何防止缓存穿透、缓存击穿和缓存雪崩？

**参考回答：**

**缓存穿透**（查询不存在的数据）：
- 解决方案：缓存空值（null）并设置较短过期时间（如 60 秒）
- 进阶方案：使用布隆过滤器（Bloom Filter）预先判断 key 是否存在

**缓存击穿**（热点 key 过期，大量请求同时打到数据库）：
- 解决方案：使用 Redisson 互斥锁，只允许一个线程去数据库查询并重建缓存，其他线程等待
- 或使用"逻辑过期"策略：缓存中不设置 TTL，而是存储一个逻辑过期时间，异步线程负责更新

**缓存雪崩**（大量 key 同时过期）：
- 解决方案：过期时间添加随机值（如基础过期时间 + 1-5 分钟的随机偏移）
- 多级缓存：本地缓存（Caffeine）+ Redis 分布式缓存，减少 Redis 压力
- 限流降级：对数据库查询接口做限流保护

## 六、RabbitMQ 消息队列

### Q16: 为什么选择 RabbitMQ 而不是 Kafka 或 RocketMQ？

**参考回答：**

选择 RabbitMQ 主要基于以下考虑：

1. **功能匹配度**：项目的消息场景主要是异步通知、事件驱动，不需要 Kafka 那样的大吞吐量日志采集能力。RabbitMQ 的 AMQP 协议功能丰富，完全满足需求。
2. **路由灵活性**：RabbitMQ 支持多种交换机类型（Direct、Topic、Fanout、Headers），可以灵活实现点对点、发布/订阅、通配符路由等模式。
3. **运维简单**：RabbitMQ 自带管理界面，消息监控、队列管理方便，且内存占用远低于 Kafka。
4. **社区生态**：Spring Boot 对 RabbitMQ 有非常成熟的自动配置支持，集成成本低。

**Kafka 更适合**的场景：海量日志收集、流式处理、大数据 pipeline。如果未来项目有用户行为日志分析的需求，可以引入 Kafka 作为补充。

### Q17: RabbitMQ 的消息可靠性如何保证？消息丢失和重复消费怎么处理？

**参考回答：**

**消息可靠性保证（三阶段）**：

1. **生产者 → 交换机**：启用 Publisher Confirm 机制，消息到达交换机后回调确认，否则重发。
2. **交换机 → 队列**：配置 Mandatory 参数，路由不到队列的消息返回生产者，记录日志或存入死信队列。
3. **队列 → 消费者**：手动 ACK（`acknowledge-mode: manual`），消费成功才确认，失败则重回队列或进入死信队列。

**消息丢失处理**：
- 持久化配置：交换机、队列、消息都设置为持久化（`durable: true`）
- 集群部署：RabbitMQ 支持镜像队列，主从节点数据同步

**重复消费处理（幂等性）**：
- 业务层实现幂等性：每条消息携带唯一业务 ID（如订单号），消费者处理前先查询是否已处理
- 使用 Redis 或数据库记录已处理的消息 ID，配合去重表实现

### Q18: 项目中定义了哪些交换机、队列和路由键？为什么这样设计？

**参考回答：**

在 `RabbitMQConfig.java` 中定义了以下几组：

| 交换机 | 队列 | 路由键 | 用途 |
|--------|------|--------|------|
| `tjnovel.notification.exchange` | `tjnovel.notification.queue` | `tjnovel.notification` | 通用通知推送 |
| `tjnovel.novel.update.exchange` | `tjnovel.novel.update.queue` | `tjnovel.novel.update` | 小说更新通知粉丝 |
| `tjnovel.order.event.exchange` | `tjnovel.order.event.queue` | `tjnovel.order.event` | 订单支付回调事件 |

**设计思路**：
- 采用 Topic 交换机，支持通配符路由，便于未来扩展
- 每个业务场景独立一套交换机和队列，避免消息相互干扰
- 路由键命名规范为 `{业务域}.{事件类型}`，便于管理和排查

## 七、Elasticsearch 全文检索

### Q19: 为什么需要 Elasticsearch？直接用 MySQL 的 LIKE 查询不行吗？

**参考回答：**

MySQL LIKE 查询的局限性：

1. **性能问题**：`LIKE '%keyword%'` 无法使用索引，必须全表扫描。当小说表和章节表达到百万级数据量时，查询耗时可能达到秒级甚至更久。
2. **搜索体验差**：MySQL 不支持中文分词、同义词、拼音纠错、相关性排序等功能。比如搜索"斗破苍穹"，包含"斗破"的结果不一定排在前面。
3. **不支持高亮**：搜索结果中无法直接标记关键词命中位置，需要前端自行处理。

**Elasticsearch 带来的提升**：
- 搜索响应时间从秒级降至毫秒级（10-100ms）
- 支持 IK 中文分词，搜索结果更精准
- 支持命中高亮（highlight），提升用户体验
- 支持相关性评分排序（TF-IDF / BM25）

### Q20: MySQL 到 Elasticsearch 的数据同步方案是什么？如何保证数据一致性？

**参考回答：**

数据同步采用 **双写 + 异步同步** 策略：

1. **双写模式**：业务写入 MySQL 后，通过 RabbitMQ 发送索引更新消息，content-service 消费消息后同步更新 Elasticsearch 索引。
2. **全量同步**：项目启动时或定期执行全量数据同步，将 MySQL 中的全部数据重新索引到 ES，确保数据一致性。

**数据一致性保证**：
- 消息队列确保 MySQL 写入和 ES 索引的最终一致性
- 定期全量同步作为兜底策略，修复可能的数据不一致问题
- 查询时以 ES 为主，但允许用户选择"精确搜索"走 MySQL 查询

### Q21: Elasticsearch 的索引结构是如何设计的？查询时如何实现高亮？

**参考回答：**

**索引结构**（以小说索引为例）：

```java
@Document(indexName = "novels")
public class NovelDocument {
    @Id
    private Long novelId;
    
    @Field(type = FieldType.Text, analyzer = "ik_max_word", searchAnalyzer = "ik_smart")
    private String novelName;        // 小说名称，IK 分词
    
    @Field(type = FieldType.Text, analyzer = "ik_max_word", searchAnalyzer = "ik_smart")
    private String authorName;       // 作者名称
    
    @Field(type = FieldType.Text, analyzer = "ik_max_word", searchAnalyzer = "ik_smart")

```

**高亮查询实现**：

```java

    .withHighlightBuilder(new HighlightBuilder()

### Q30: 如果小说详情页面临高并发访问，如何设计缓存策略？

```
请求 → CDN (静态资源) → Nginx 本地缓存 → Redis 分布式缓存 → MySQL

3. **Redis 层**：缓存小说详情、最新章节列表等信息
4. **本地缓存层**：使用 Caffeine（本地缓存）缓存最热门的 1000 本小说，过期时间 60 秒
5. **数据库层**：作为最终数据源，通过限流保护

**缓存更新策略**：当作者更新小说信息时，通过 RabbitMQ 广播缓存失效消息，各层缓存逐级清除。

1. **索引优化**：通过慢查询日志（`slow_query_log`）定位慢 SQL，使用 `EXPLAIN` 分析执行计划，添加合适的索引
2. **分页优化**：大偏移量分页使用"子查询优化"或"游标分页"替代传统 `LIMIT offset, size`
3. **查询优化**：避免 `SELECT *`，只查询需要的字段；使用覆盖索引减少回表查询
4. **连接池调优**：合理配置 HikariCP 的 `maximumPoolSize`（根据 `max_connections` 和业务并发量计算）

**典型慢查询场景**：小说列表按时间倒序 + 大偏移量分页。优化方案：使用 `WHERE id > ? ORDER BY id` 替代 `LIMIT 100000, 20`。

## 十二、安全性设计

### Q32: JWT 认证是如何实现的？Token 刷新和续期怎么做？

**参考回答：**

**JWT 实现流程**：
1. 用户登录成功后，user-service 生成 JWT Token（包含 `iss`、`aud`、`sub`、`exp` 等声明）
2. 前端将 Token 存储在 localStorage 或 Pinia store 中
3. 后续请求在 Authorization 头中携带 `Bearer {token}`
4. Gateway 层或各微服务的 SecurityConfig 中验证 Token 的有效性

**JWT 配置**：
```yaml
jwt:
  issuer: tj-novel
  audience: tj-novel
  key: your-256-bit-secret-key-here
  expiration: 7200000  # 2小时
```

**Token 刷新策略**：
- Token 过期时间设置为 2 小时
- 前端在 Token 过期前（如剩余 30 分钟）自动调用刷新接口
- 刷新接口验证旧 Token 的签名和声明，签发新 Token
- 如果 Token 已过期，要求用户重新登录

### Q33: 密码是如何存储的？如何防止 SQL 注入和 XSS 攻击？

**参考回答：**

**密码加密**：
- 使用 PBKDF2WithHmacSHA256 算法，迭代 10000 次，密钥长度 120 位
- 固定 Salt + 密码作为输入，输出 Base64 编码后截取前 20 个字符
- 与原有 Backend 保持算法一致，确保用户数据可以无缝迁移

**SQL 注入防护**：
- 使用 MyBatis-Plus 的 `#{}` 占位符（预编译 + 参数化查询），避免 SQL 拼接
- LambdaQueryWrapper 类型安全，天然防止注入
- 输入校验：后端对用户输入进行长度、格式校验

**XSS 防护**：
- 前端 Element Plus 组件默认对用户输入进行转义
- 后端对用户输入进行 HTML 标签过滤
- 评论、小说内容等富文本场景使用白名单标签策略

### Q34: 微服务之间如何保证安全通信？是否使用了 API 签名或鉴权？

**参考回答：**

**当前实现**：
- 内部服务间通信通过 Docker 内部网络，不对外暴露端口，默认信任内部网络
- 对外接口统一通过 Gateway 暴露，Gateway 层进行身份认证
- 各微服务通过 Spring Security 配置接口访问权限，区分公开接口和需认证接口

**未来改进方向**：
- 内部服务间引入 JWT 或 API Key 认证，防止内部接口被非法调用
- 使用 mTLS（双向 TLS）加密服务间通信
- 引入 OAuth2 或 Spring Security 的 @PreAuthorize 实现细粒度权限控制

### Q36: 在项目开发过程中遇到的最大技术挑战是什么？如何解决的？

**参考回答：**

**最大挑战：数据一致性保障**

在微服务架构中，一个业务操作往往涉及多个服务。例如"用户购买章节"涉及：
1. transaction-service：扣减余额、创建订单
2. content-service：解锁章节权限
3. notification-service：通知作者

如果某个环节失败，如何保证数据一致性？

**解决方案**：
1. **本地事务 + 消息队列**：核心业务操作使用本地事务保证 ACID，事务成功后发送消息到 RabbitMQ，下游服务通过消费消息完成后续操作
2. **消息幂等性**：每条消息携带唯一业务 ID，消费者通过去重表保证只处理一次
3. **死信队列 + 重试机制**：消费失败的消息进入死信队列，通过重试 + 人工补偿机制保证最终一致性
4. **分布式锁**：针对防重复充值、防重复打赏等场景，使用 Redisson 分布式锁保证同一时间只有一个请求能处理

### Q40: 如果用户反映"小说搜索太慢"或"支付超时"，你会如何排查问题？

**参考回答：**

**场景一：小说搜索太慢**

排查步骤：
1. **检查慢查询日志**：确认是否走了 ES 还是 MySQL（如果 ES 不可用，代码是否有降级策略）
2. **查看 ES 集群状态**：`GET /_cluster/health` 检查节点状态、分片分配情况
3. **分析查询性能**：使用 Kibana 的 Search Profiler 分析查询耗时分布
4. **检查索引大小**：确认索引是否需要优化（合并段、刷新间隔）
5. **查看系统资源**：ES 节点的 CPU、内存、磁盘 I/O 是否达到瓶颈

**场景二：支付超时**

排查步骤：
1. **查看日志链路**：从 Gateway 日志 → transaction-service 日志 → 数据库日志，定位超时环节
2. **检查数据库连接池**：`SELECT * FROM information_schema.processlist` 查看是否有锁等待
3. **检查 Redis 连接**：确认分布式锁是否正常获取和释放
4. **检查消息队列**：确认订单消息是否正常投递和消费
5. **查看系统资源**：CPU、内存、网络延迟是否正常

### 回答问题的 STAR 原则

| 要素 | 说明 | 示例 |
|------|------|------|
| **S**ituation | 背景是什么 | 项目需要从 Azure 云迁移到本地部署 |

### 加分项

- **量化成果**：尽量用数据说话，如"搜索响应时间从 2 秒降至 50 毫秒"
- **体现思考**：不仅说做了什么，还要说为什么这么做、有没有其他方案
- **展现学习能力**：遇到不熟悉的技术时，如何快速学习并应用到项目
- **承认不足**：主动提及项目的待改进点，展现技术视野和成长性
