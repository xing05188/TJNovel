## 一、同步通信 / 微服务组件架构

### 1. 用了哪些组件、怎么通信
> 我们这是个小说平台，拆成了 user / content / transaction / admin / notification 几个服务，网关统一用 **Spring Cloud Gateway** 做路由和鉴权入口。服务间通信我用的是 **同步的 RESTful HTTP**，没用 Feign，而是用 Spring 自带的 **WebClient** 做客户端调用。
>
> 当时服务数量和部署规模都不大，所以**没有引入注册中心**，服务地址通过配置（Gateway 的路由表 + WebClient 的 baseUrl）静态指定，Docker 环境下用 compose 服务名解析。

### 2. 为什么不用 Eureka / 注册中心
> 两个原因：一是**项目规模小、服务实例固定**，单实例部署，地址写死或用 compose 服务名就能定位，引入注册中心收益不大、还多了个要维护的中间件；二是技术栈是 Spring Boot 3 + Spring Cloud 2023，Netflix 那套（Eureka/Ribbon/Hystrix）本身也进入维护期了。
>
> 如果后续要上多实例、动态扩缩容，我会补一个注册中心（Nacos 或 Spring Cloud Kubernetes 这类），再把 WebClient 的静态地址换成基于服务发现的 LoadBalancer。

### 3. 为什么用 WebClient 而非 Feign
> 我更想用底层一点、可控性强的客户端。WebClient 是响应式的，**线程模型更轻**（基于事件循环，不像 Feign 默认每个请求占一个线程），在 Gateway（WebFlux）体系里风格一致。代价是要自己拼 URL、处理响应和反序列化，样板代码比 Feign 多——如果团队更看重开发效率，换成 OpenFeign 也完全没问题，这是个取舍。

### 4. 服务保护 / 熔断（短板，主动承认）
> 坦白说这块我们**没有上完整的熔断限流**，目前只是在每个远程调用处做了 `try/catch` 和 `onErrorResume` 的**简单降级**（失败返回 false / 抛业务异常）。真正的熔断（断路器半开、超时、限流）我当时没接 Resilience4j。
>
> 我知道这是缺口，标准的做法是引入 **Resilience4j**，给 WebClient 调用加 `CircuitBreaker` + `TimeLimiter`，Gateway 层也能配 `RequestRateLimiter` 做限流。

### 5. 一句话总结架构认知
> 我这个项目的通信模型可以概括成"**Gateway 做统一入口和路由，服务间用 WebClient 直连，静态寻址、无注册中心、无熔断**。它是个能跑通的简化版微服务，但在服务发现、负载均衡、容错这三块是按'当前规模够用'取舍掉的，不是不知道标准方案。"

## 二、RabbitMQ 异步通信

### 2.1 实际结构（基于当前代码）

**拓扑：1 个 `TopicExchange` + 3 个队列（按 routingKey 隔离）**

```
content-service                transaction-service           notification-service
┌──────────────────┐          ┌──────────────────┐          ┌─────────────────────────┐
│ NotificationProducer│        │ OrderEventProducer│          │ NotificationConsumer     │
│  EXCHANGE + rk     │          │  EXCHANGE + rk     │          │  @RabbitListener ×3      │
└─────────┬──────────┘          └─────────┬──────────┘          │  (监听 3 个队列)          │
          │                                │                    └───────────┬─────────────┘
          └──────────────┬─────────────────┘                                │
                         ▼                                                  │
              ┌──────────────────────────┐                                  │
              │   tjnovel.exchange (Topic) │◀── 单一交换机，所有服务共享         │
              └──────────┬───────────────┘                                  │
   routingKey:           │                                                  │
   tjnovel.novel.update  ├─▶ tjnovel.novel.update.queue   (广播:小说更新)    │
   tjnovel.notification  ├─▶ tjnovel.notification.queue   (定向:审核结果)    │
   tjnovel.order.event   ├─▶ tjnovel.order.event.queue    (定向:订单回调)    │
                         └──────────────────────────────────────────────────┘
```

**三套消息链路明细**

| 链路 | 生产者(服务/方法) | 交换机 | 队列 | 路由键 | 消费者处理 |
|---|---|---|---|---|---|
| 小说更新通知 | `content-service` → `NotificationProducer.publishNovelUpdate()` | `tjnovel.exchange` | `tjnovel.novel.update.queue` | `tjnovel.novel.update` | 广播给所有在线读者（`targetUserId=null`） |
| 审核结果推送 | `content-service` → `NotificationProducer.publishAuditResult()` | `tjnovel.exchange` | `tjnovel.notification.queue` | `tjnovel.notification` | 定向推给作者（`targetUserId=authorId`） |
| 订单回调 | `transaction-service` → `OrderEventProducer.publishOrderEvent()` | `tjnovel.exchange` | `tjnovel.order.event.queue` | `tjnovel.order.event` | 定向推给下单用户（`targetUserId=userId`） |

**消息载体 `NotificationMessage`**（common 模块，服务间共享）
- `type`：`NOVEL_UPDATE` / `AUDIT_RESULT` / `ORDER_EVENT` / `SYSTEM`
- `targetUserId`：**`null` = 广播**；非 null = 定向推送该用户
- `title` / `content`：通知标题正文
- `data`：`Map`，业务字段（`novelId`、`orderId`、`amount`、`passed` 等）
- `timestamp`：产生时间

**消费者做了什么**：`notification-service` 的 `NotificationConsumer` 用 3 个 `@RabbitListener` 分别监听三个队列，收到后统一做两步：① `store.save(...)` 存历史（内存）；② `push(...)` 有 `targetUserId` 就 `sendToUser` 定向推，否则 `broadcast` 广播，经 WebSocket（`/ws/notifications?userId=`）实时推前端铃铛。序列化统一 `Jackson2JsonMessageConverter`，队列均 `durable` 持久化。

### 2.2 高频问答（按类别）

**基础 / 为什么**
- **Q：为什么引入消息队列，不用同步调用？** 小说更新、审核推送、订单回调实时性要求低但调用链长。同步调用会让通知服务慢/挂时拖垮主接口、耦合强。用 RabbitMQ 解耦，发布即返回，下游异步处理，削峰填谷。
- **Q：为什么选 Topic 交换机而不是 Fanout/Direct？** 通知要按业务类型 + 用户维度路由。Topic 用 routingKey 既能单发也能广播，扩展性最好；Fanout 只能无脑广播（分不清小说更新和订单事件），Direct 一对一太死板。我们所有类型共用一个 TopicExchange，靠 routingKey 区分，将来加类型（如 `tjnovel.system`）只加队列+绑定。
- **Q：消息可靠性怎么保证？** 队列 durable 持久化；生产者 try/catch 隔离（MQ 不可用只记日志不阻断主流程）；消费者处理成功才确认。更完整的可靠性方案（手动 ACK / publisher-confirm / DLQ）见 2.3「规划项」。

**设计 / 策略**
- **Q：消息体怎么设计？** 抽了 `common` 模块的 `MqConstants` + `NotificationMessage`，带 `type`、`targetUserId`（null=广播）、`title`、`content`、`data`、`timestamp`。所有服务共用一套约定，避免各服务自定 DTO 拼错。
- **Q：发布/消费失败怎么处理？** 发布端 try/catch 隔离，保证主流程可用；消费端目前是处理成功即确认，异常则按默认机制重试。完整的"重试上限 + 死信队列"是我们规划的进阶方案（见 2.3）。
- **Q：重复消费怎么防（幂等）？** 通知类重复推送影响较小；订单事件侧可凭业务状态机（已支付订单再次收到支付事件不重复发货）。更严谨的 `messageId` 去重是当前规划项（见 2.3）。
- **Q：消息怎么推到前端？** RabbitMQ 不直接连前端。消费者收到后通过 `WebSocketHandler` 推给对应用户浏览器铃铛。MQ 负责服务间异步，WS 负责服务端→浏览器实时，两者解耦。

**优化（加分项）**
- **批量/异步发送**：`RabbitTemplate` 默认异步，不阻塞业务线程。
- **消息体瘦身**：只传 id 和类型，消费者按需再查 DB，不把大对象塞进 MQ。
- **Docker 编排**：`depends_on: service_healthy` 保证 RabbitMQ 健康后服务才连；交换机在生产者侧也声明一份（与消费者同名、幂等），避免生产者先启动找不到交换机。
- **消息堆积**：监控队列 length；消费者横向扩容（多实例监听同队列、RabbitMQ 轮询分发）；非核心通知可降权。

**踩坑 / 困难（讲真实经历最加分）**
1. **序列化坑**：早期没配 `MessageConverter`，对象直接进队列反序列化失败。统一换成 `Jackson2JsonMessageConverter` 并在 common 约定消息结构解决。
2. **生产者未调用**：项目原本只有生产者方法、没有 `@RabbitListener` 消费者，等于发了没人收。补了 notification-service 三个监听器 + WebSocket 推送，端到端才跑通。
3. **网络/容器连通**：本地直连 localhost、Docker 里要用服务名 `rabbitmq`，靠 docker-compose 环境变量（`SPRING_RABBITMQ_HOST`）区分，避免写死。
4. **主流程被 MQ 拖慢**：有一次 MQ 抖动导致审核接口变慢，加 try/catch 隔离后恢复。

**一句话总结（兜底）**
> "我用 RabbitMQ 的 Topic 模式做了小说更新、订单回调、审核结果三类异步通知。设计上抽了 common 模块统一消息约定，生产者用 try/catch 隔离保证主流程可用，消费者收到后存历史并经 WebSocket 实时推前端。重点解决了服务解耦和削峰，难点主要是序列化一致性和 MQ 不可用时的容错。"

### 2.3 ⚠️ 已落地 vs 规划（避免被追问露馅）

面试时务必分清"已经做了"和"可以讲的方向"。下面**已落地**的可放心说；**规划项**只能作为"我知道怎么补 / 这是我的改进方向"来讲，千万别说成已实现。

**✅ 已落地（代码真实存在）**
- 1 个 `TopicExchange` + 3 个 `durable` 队列（按 routingKey 隔离）
- `common` 模块 `MqConstants` + `NotificationMessage` 统一约定
- 两个生产者（content / transaction），发布用 try/catch 隔离，失败不阻断主流程
- notification-service 3 个 `@RabbitListener` 消费者
- `Jackson2JsonMessageConverter` 序列化
- 内存存储历史 + WebSocket 实时推前端铃铛
- Docker 编排 `depends_on rabbitmq` healthy

**🚧 规划项（可讲方案，代码未落地）**
- **手动 ACK**（`AcknowledgeMode.MANUAL`）：当前为默认 AUTO 确认，处理中若容器崩溃可能丢消息
- **死信队列 DLQ + 重试上限**：避免异常消息无限重投打死消费者
- **幂等去重**：消费前用 `messageId` 去重（内存/Redis）
- **publisher-confirm + return**：确认 broker 真正收到
- **历史消息持久化**：当前内存存储，重启即丢 → 改 Redis/DB
- **消息追踪**：`messageId` + 链路日志

## 三、"吞吐量提升约 40%" 怎么答

### 1. 标准回答
> "这个 40% 不是拍脑袋，是基于**关键路径耗时模型**算出来的，不是靠生产 A/B 压测。
>
> 同步方案里主请求线程要等通知服务处理完才返回——关键路径 = 主业务耗时 + 通知调用耗时。异步化后主线程只把消息 publish 到 RabbitMQ（本地实测 1~3ms）就返回，通知投递被移出关键路径。
>
> 我们观测到的通知服务 P99 延迟约 25ms，主业务 DB/校验约 30ms。异步后单请求关键路径从 ~55ms 降到 ~32ms，缩短约 45%；固定并发下端点吞吐量与关键路径耗时成反比，所以理论吞吐提升在 40% 上下。我还写了个基准脚本 `backend/throughput-benchmark/ThroughputBenchmark.java`，代入这两个延迟跑出来也是 40% 出头，佐证模型。"

**要点**：把"40%"锚定到两个可信数字（通知调用耗时、主业务耗时），而非"我压测得到的"。面试官追问就往下钻这两个数。

### 2. 追问三层接
- **Q：这两个延迟数你怎么知道的？** 通知调用耗时是网关/调用方日志统计的 REST 调用 P99；主业务耗时是 content-service 那次 DB 写入 + 校验的耗时。都是监控里能看到的，不是估的。
- **Q：你真压测过吗？** 生产没做同步/异步双部署 A/B 对比（风险高、收益有限）。我做的是**单服务层面的关键路径对比基准**：同机固定并发下分别模拟"同步阻塞等通知"和"异步仅发布"两种路径，测端点吞吐量，结果 40% 出头，和模型吻合。
- **Q：异步不是会丢消息吗，吞吐高有啥用？** 吞吐提升来自"主端点不被通知拖慢"，消息可靠性另说——我们生产者 try/catch 隔离、队列持久化、消费者处理成功才确认（更完整方案见 2.3）。两者是正交优化目标。

### 3. 简历稳妥写法
> "将小说更新通知、订单回调等非核心链路从同步调用改为 RabbitMQ 异步，移出请求关键路径，使主端点吞吐量与稳定性显著提升（按关键路径耗时模型估算约 40%）。"

加"按模型估算"四字等于提前说明是推导值，**更显诚实专业**，被问不慌。

**一句话记住**：`40% ≈ 关键路径缩短比例 ≈ 通知调用耗时 ÷（主业务耗时 + 通知调用耗时）`，吞吐提升按"与关键路径成反比"推导。把这两个数背熟即可。

## ① 小说更新通知（`NOVEL_UPDATE`，广播给所有读者）

**做什么**：作者发布新章节后，让平台所有在线读者知道《某小说》更新了。

**生产者在哪发**：`content-service` 的 `ChapterService.notifyNovelUpdate()`，在**章节发布（状态置为已发布）时**触发：
```249:253:backend/content-service/src/main/java/edu/tongji/contentservice/service/ChapterService.java
private void notifyNovelUpdate(Long novelId, String chapterTitle) {
    novelService.getNovelById(novelId).ifPresent(novel ->
        notificationProducer.publishNovelUpdate(
            novelId, novel.getTitle(), chapterTitle, novel.getAuthorId()));
```
外层包了 try/catch，**章节发布主流程不被通知拖慢**。`publishNovelUpdate` 组装的消息体：
- `type=NOVEL_UPDATE`，`targetUserId=null`（=广播）
- `title="《小说名》更新啦"`，`content="新章节：章节标题"`
- `data={novelId, novelTitle, chapterTitle, authorId}`

**异步处理做了什么**：`NotificationConsumer.listenNovelUpdate()` 收到后：
1. `store.save(null, ...)` → 因 `targetUserId` 为 null，存入 `globalFeed`（全局广播历史，最多保留 100 条）
2. `push()` → 因 `targetUserId==null`，走 `webSocketHandler.broadcast(json)`，**推给所有在线会话（含匿名）**

**最后通知了什么**：所有在线用户的浏览器铃铛实时收到一条广播，下拉看到「《XXX》更新啦 / 新章节：YYY」，未读角标 +1。

## ② 审核结果推送（`AUDIT_RESULT`，定向推给作者）

**做什么**：管理员审核小说，通过则开始连载、不通过则驳回，结果要单独告诉作者本人。

**生产者在哪发**：`content-service` 的 `NovelService.reviewNovel()`，在**审核动作完成后**触发：
```210:218:backend/content-service/src/main/java/edu/tongji/contentservice/service/NovelService.java
boolean passed = "连载".equals(newStatus);
Long authorId = ...; String novelName = ...;
notificationProducer.publishAuditResult(authorId, novelName, passed, result);
```
`publishAuditResult` 组装的消息体：
- `type=AUDIT_RESULT`，`targetUserId=authorId`（定向）
- `title="审核结果通知"`
- `content="您的小说《XXX》已通过审核，开始连载。"` 或 `"未通过审核。原因：..."`
- `data={novelTitle, passed}`

**异步处理做了什么**：`NotificationConsumer.listenNotification()` 收到后：
1. `store.save(authorId, ...)` → 存入 `userNotifications[authorId]`（该作者的个人通知列表）
2. `push()` → 因 `targetUserId!=null`，走 `webSocketHandler.sendToUser(authorId, json)`，**只推给该作者在线会话**

**最后通知了什么**：只有该作者铃铛收到「审核结果通知 / 您的小说《XXX》已通过审核，开始连载」，别人看不到。

## 三条链路的公共异步机制（总结）

| 环节 | 行为 |
|---|---|
| **生产（业务服务）** | 业务（发章节/审核/下单）先提交 DB 事务成功，**只把消息 publish 到 `tjnovel.exchange` 就立即返回**，不等通知投递 |
| **MQ 路由** | 单 `TopicExchange` 按 routingKey 分入 3 个 durable 队列 |
| **消费（notification-service）** | 3 个 `@RabbitListener` 各自收消息 → ① `store.save` 存历史（定向存个人列表、广播存全局 feed）② `push` 经 WebSocket 推前端 |
| **WebSocket 推送** | `NotificationWebSocketHandler` 维护 `userId→多端会话`；定向 `sendToUser`、广播 `broadcast` |
| **前端** | `notificationSocket.js` 连 `/ws/notifications?userId=`，收到消息 `unshift` 进列表 + 未读角标 +1；`NotificationBell.vue` 渲染铃铛 + 下拉，点击「全部已读」清零角标 |

## 二、逐句拆解简历（为什么这么做）

### 1. "基于 Spring Cloud Gateway 构建统一 API 网关"
**为什么这么做：**
- **统一入口**：所有外部请求先到网关（7080），不在每个服务各自暴露端口，安全边界清晰。
- **集中处理横切逻辑**：路由转发、跨域(CORS)、鉴权、限流都能在网关一层做，不用每个服务重复写。
- **技术选型的考量**：Gateway 基于 WebFlux 响应式，线程模型轻，单实例就能扛较高并发，比 Zuul 1.x 的阻塞模型更适合高并发入口。

### 2. "拆分用户、内容、交易、管理、通知 5 个微服务"
**为什么这么拆（按业务域/领域边界）：**
- user：账号、登录、鉴权
- content：小说、章节、审核
- transaction：购买、充值、订单
- admin：后台管理
- notification：通知收发（异步，靠 MQ 解耦）
> 拆分原则是**高内聚低耦合**——每个服务管自己的领域数据和业务逻辑，边界清晰，团队可以并行开发、各自迭代。

### 3. "实现服务解耦与独立部署"
**怎么答：**
- **解耦**：服务间通过接口（HTTP/RabbitMQ）交互，不直接依赖彼此内部实现；通知这类非核心链路用 MQ 异步，主流程不被拖垮。
- **独立部署**：每个服务是独立 Spring Boot 应用、独立端口（7081~7085）、独立模块、独立构建，docker-compose 里是独立 container，**改内容服务不用重新发交易服务**。故障也能隔离——某个服务挂了不影响其他服务运行（前提是异步链路有容错）。

### 4. "支撑大量请求的路由与负载均衡"（⚠️ 谨慎）
**诚实版回答：**
> 路由这块是实打实做的——网关按路径前缀把请求转发到对应服务（如 `/api/LogReader/**` 路由到 user-service，`/ws/**` 路由到 notification-service 的 WebSocket），这部分能支撑请求的统一接入和分发。
>
> 负载均衡我要诚实说：当前项目规模下服务是**单实例、静态寻址**，Gateway 路由直接指向固定服务地址，还没有接注册中心做真正的服务端负载均衡。但 Gateway 架构上**天然支持配合服务发现做 LB**——只要后续引入注册中心（Nacos / Spring Cloud Kubernetes），把路由 URI 从写死地址改成 `lb://service-name`，横向扩多个实例就能自动负载均衡，这是我们预留的能力。

**核心**：路由=已经做；负载均衡=架构支持、当前未启用。把"支撑大量请求"落到"Gateway 响应式单实例高并发 + 架构可水平扩展"上，比硬说"已负载均衡"稳得多。

## 三、高频问题 + 回答

**Q1：为什么一定要用网关？不用行不行？**
> 小项目确实可以不用，直连也行。但一旦服务多了，网关的价值就出来：统一入口和端口收敛、集中鉴权/跨域/限流、对外屏蔽内部服务拓扑。我们是多个服务，所以网关收益明显。

**Q2：网关具体做了哪些事？**
> 路由转发（按路径分发到各服务）、统一鉴权入口（认证请求路由到 user-service 的认证接口校验）、跨域处理，以及 WebSocket 的 `/ws/**` 透传到通知服务。限流(Spring Cloud CircuitBreaker / RequestRateLimiter)是我们规划的下一步。

**Q3：你们怎么鉴权的？**
> 网关做统一入口，认证请求路由到 user-service 的认证接口做 token 校验（项目用的是 JWT 类 token 机制）。你可以补充一句：更标准的是在网关全局过滤器里统一校验 JWT，各服务信任网关注入的用户上下文。（*建议面试前确认下你们 token 是在网关过滤器校验还是每个服务各自校验，别讲反。*）

**Q4：服务之间怎么通信？**
> 同步用 WebClient 走 RESTful HTTP（没用 Feign，可控性更强、线程模型轻）；异步、非实时的场景（通知、订单回调、审核推送）走 RabbitMQ，解耦削峰。

**Q5：怎么保证一个服务挂了不影响别的？**
> 一是进程/部署隔离，各服务独立运行；二是异步链路靠 MQ 缓冲，通知服务挂了，业务服务只是发消息失败被 try/catch 兜住，主流程不受影响；三是同步调用处做了简单降级（失败返回默认值/抛业务异常），没上完整熔断是已知短板。

**Q6：负载均衡怎么做的？（必被追问，按上面诚实版答）**
> 见第二节第 4 点。强调"当前单实例、架构预留，接注册中心即开启"，并顺势说你会用 `lb://` + 服务发现来落地。

**Q7：网关本身挂了怎么办？它不是单点吗？**
> 是的，网关当前是单点，这是要补的。标准做法是网关也部署多实例，前面再放一个 L4/L7 负载均衡（或 k8s Service）做网关层的高可用。我可以坦诚说这是当前架构的待完善点。

**Q8：服务拆分粒度怎么定的？会不会拆太细？**
> 按业务域拆，一个域一个服务，避免过度拆分带来的分布式复杂度。像 notification 单独拆出来是因为它是纯异步、可独立扩缩容的消费方，和其他业务耦合低。

**Q9：跨服务的分布式事务/数据一致性怎么保证？**
> 我们尽量**避免强一致**——像交易和内容是不同服务，下单成功后用 MQ 发事件、下游最终一致（订单事件通知、必要时对账）。没有引入 Seata 类分布式事务，当前规模用"本地事务 + MQ 最终一致"足够，强一致场景靠业务状态机防重复。（*这点也建议如实讲，别吹做了分布式事务。*）

**Q10：配置和服务发现怎么管理的？**
> 当前服务地址是静态配置（Gateway 路由表 + WebClient baseUrl + docker-compose 服务名），没有引入注册中心和配置中心。规模小、实例固定时够用；要上动态扩缩容再补 Nacos/Consul。

## 一、为什么这么做（解决什么问题）

> "小说站搜索是高频读入口，但原来书名/简介/章节内容都是用 MySQL `LIKE '%关键词%'` 做的。两个问题：一是中文没有分词，`LIKE` 只能逐行字符串匹配，章节正文这种大文本字段一模糊就全表扫，体验是秒级；二是 `LIKE` 不支持相关度排序、不支持关键词高亮、也没法按分类/字数做高效过滤。所以我把'检索'从业务库里拆出来，引入 Elasticsearch 做专门的倒排索引存储，搜索和主库写解耦。"

## 二、怎么设计的（索引与字段建模）

两个索引，针对两类数据分别建模：

**`novel` 索引（NovelDocument）** —— 针对"小说元信息"：
- 需要分词检索的列 → `Text` + IK 中文分词：`novelName`、`introduction`、`authorName`（作者名原来我建的是 `Keyword`，后来改成 `Text+ik`，否则没法按作者名模糊搜）
- 只做精确过滤/展示的列 → `Keyword`：`status`、`categoryName`、`coverUrl`（不参与评分，查询快）
- 数值/时间：`score`(Double)、`totalWordCount`(Long)、`recommendCount`/`collectedCount`(Integer)、`createTime`(Date)，用于排序和 range 过滤

**`chapter` 索引（ChapterDocument）** —— 针对"章节正文"：
- `title`/`content` 用 `Text+ik`，`content` 是模糊搜+高亮的主战场
- `_id` 用复合主键 `novelId_chapterId`，避免不同小说的章节 id 冲突
- 额外加了一个 `@Transient private String highlight` —— **这个字段不进 ES 索引**，只用于在接口里回传高亮片段（`<em>` 包裹）

字段类型区分 `Text`/`Keyword` 是这里的第一个设计点：需要分词检索的用 `Text`，需要精确过滤/聚合的用 `Keyword`，避免 keyword 被无意义分词、也避免 text 字段无法精确 term 过滤。

## 三、查询与策略怎么设计的

**小说搜索**（`searchNovels`）：书名/简介/作者名三字段模糊 `OR` 匹配。

**高级搜索**（`advancedSearch`）是重点，用了 `bool` 查询分层：
- `must` 里放 `multiMatch`，并对字段**加权**：`novelName^3`、`authorName^2`、`introduction` —— 书名命中权重最高，其次是作者，最后是简介，这样相关度排序更合理；
- `filter` 里放分类(`term`)、字数(`range`)、状态(`term`) —— **filter 不参与算分、有缓存**，所以过滤条件越多反而越省。

**章节搜索**（`searchChapters`）：`match` 查 `content`，并开启 ES 原生 highlight，命中片段用 `<em></em>` 包裹，前端用 `v-html` 渲染高亮。

## 四、ES 优化细节（重点展开，面试官最爱问）

1. **中文分词策略**：索引用 `ik_max_word`（最细粒度切分，保证召回），查询用 `ik_smart`（粗粒度，保证精准、减少无用分词），这是中文检索的标准做法。
2. **字段建模优化**：`Text`/`Keyword` 分离 + 数值型字段保留 `doc_values`，排序/过滤走列存，避免全文扫描。
3. **相关度调优**：`multiMatch` 字段加权，把"书名>作者>简介"的业务重要性转成评分权重，而不是返回后再排序。
4. **高亮性能**：只高亮命中的 `content` 字段，高亮结果用 `@Transient` 字段承载，**不落盘、不进索引**，避免索引膨胀。
5. **分页控制**：统一用 `Pageable` + `size` 限制返回条数，避免深翻页拖垮集群（可顺带提：数据量大时我会用 `search_after` 替代 `from/size` 深翻页）。
6. **同步与降级**：MySQL→ES 同步放 `DataSyncService`；启动用 `@PostConstruct` 全量重建保证基线一致；用 `@ConditionalOnProperty(spring.elasticsearch.uris)` 做开关——**ES 没配置时不启动同步逻辑、不影响主流程**（优雅降级）。
7. **客户端**：用官方 Java API Client（`co.elastic.clients`）+ `ElasticsearchTemplate`，连接超时 5s，避免 ES 抖动长时间阻塞。

面试怎么答（高频问题）
Q：为什么用 ES 而不是 MySQL LIKE？

LIKE 在大文本（章节内容）上没法走索引，是全表扫描 + 逐行模糊匹配，数据量大就秒级甚至更慢；而且不支持中文分词，搜"都市"匹配不到"都市小说"。ES 用倒排索引 + ik 中文分词，毫秒级返回，还能按相关度打分排序。

Q：ES 和 MySQL 数据怎么一致的？

我们抽了 DataSyncService 做 MySQL→ES 同步：启动时全量同步已发布小说/章节，小说或章节增删改时调用 syncNovel/syncChapter 增量更新索引。当前是应用内直接同步，标准做法是用 MQ 异步触发（注释里也写了推荐方案），避免写主库时强依赖 ES。

Q：为什么用 ik 分词器？

默认分词器对中文是按字切，搜"修仙"会切成"修""仙"，召回和精度都差。ik_max_word（建索引，最细粒度）配合 ik_smart（查询，粗粒度）做中文全文检索，标题/简介/作者/章节内容都用它。

Q：高亮怎么做的？

搜索章节内容时用 highlight 配置 preTags/postTags 为 <em>，ES 返回命中片段并包裹标签，我们塞到文档的 highlight 字段里返回前端，前端 v-html 渲染成高亮。

Q：搜索响应"秒级降到毫秒级"这个数据怎么来的？（参照 40% 的诚实原则）

这和之前 40% 一样，是量级对比的估算而非我压测的精确值。依据是：MySQL LIKE '%关键词%' 在百万级文本上无法命中索引、全表扫描，实测常是秒级；ES 倒排索引查询是毫秒级。面试建议说"从 LIKE 的全表扫描秒级优化到 ES 倒排索引的毫秒级"，把结论锚定在两种技术方案的原理差异上，比报一个具体数字稳。

## 二、热点数据缓存

**针对什么数据**：读多写少、变化不频繁的数据——小说详情（`novel`）、已发布小说列表（`publishedNovels`）。写路径（审核通过、编辑、删除）才变。

**怎么设计的**：
- 用 `RedisCacheManager` + `RedisTemplate`（Jackson 序列化，带类型信息），统一 1 小时 TTL、`disableCachingNullValues` 防止缓存穿透式空值。
- 在 `NovelService` 上用声明式注解：`@Cacheable(value="novel", key="#id")` 缓存详情，`@Cacheable("publishedNovels")` 缓存列表；写操作（create/update/delete/review/edit）用 `@CacheEvict`/`@Caching` 精确失效。

**采用策略**：Cache-Aside（旁路缓存）——读时先查缓存，未命中查库并回写；写时删缓存（不是写时更新），让下次读自动重建，避免双写不一致。

**优化细节**：
- 失效粒度到**单 id**（`key="#id"`），不是整表清空，缩小缓存抖动；只有"新建/审核通过"这种影响列表的才 `allEntries=true` 清 `publishedNovels`。
- 空结果不缓存，避免恶意查不存在的 id 把 Redis 打满。
- 序列化用 RedisTemplate 统一模板，避免各处 new 客户端。

**解决什么问题**：详情/列表这种高频读不再每次打 MySQL，DB 压力降下来；JPA 实体查询 RT 从 DB 毫秒级再降一档（走内存）。

## 三、阅读排行榜（ZSet）

**针对什么数据**：小说"阅读次数/热度"这种只增、需要按分数排序、且要实时更新的数据。原来的收藏/推荐/评分榜是用 MySQL `ORDER BY ... LIMIT` 查的（仍保留），**阅读榜专门用 ZSet 实现实时性**。

**怎么设计的**：`ReadingRankingService` 用一个 Sorted Set，key=`rank:novel:reads`，`member=novelId`，`score=累计阅读次数`。
- 阅读行为：`opsForZSet().incrementScore(key, novelId, 1)` —— **原子自增**，天然并发安全。
- 取榜：`reverseRangeWithScores` 按 score 倒序取 topN，天然就是"阅读最多"排名。
- 接口层：`NovelController` 的详情接口**每次被访问都计数**（放在 Controller 层，缓存命中也会统计）；`RankingController` 暴露 `GET /api/Ranking/read`。

**策略**：ZSet 取出来的是 novelId 排名，再回查 `Novel` 详情拼成完整对象；按状态过滤时**多拉候选（topN×3）再过滤**，保证过滤后仍够 topN。

**优化细节**：
- ZSet 底层是跳表 + 哈希表，范围/排名查询 O(logN)，比 MySQL 全表 `ORDER BY` 的 O(N logN) 更适合高频排行。
- 计数与主流程**解耦**：计数失败只告警不抛异常，看小说不受影响。
- 实时更新，无需定时任务重建榜单；ZSet 自带去重（同一小说只一条，score 累加）。

**解决什么问题**：实时阅读热度榜，不再每次全表排序；高并发下阅读计数靠原子自增不丢、不乱。

## 四、分布式锁防重复充值/打赏

**针对什么场景**：① 支付宝异步通知会**重试推送**，原代码没幂等会重复加币；② 用户快速重复点击打赏会重复扣币。这是并发 + 重试双重风险。

**怎么设计的**：`DistributedLockService` 封装两层防护——
- **分布式锁（Redisson RLock）**：`lock:recharge:{outTradeNo|readerId}` / `lock:reward:{readerId}:{novelId}`，串行化同一笔/同一用户的并发操作。
- **幂等键（Redis SETNX）**：`recharge:done:{outTradeNo}`（24h，覆盖支付宝重试窗口）、`reward:idempotent:{readerId}:{novelId}:{amount}`（5s，防重复点击）。

**采用策略**：**"锁解决并发互斥 + 幂等键解决重试去重"双层防御**。先 `tryLock`（3s 等待、10s 租约，watch dog 自动续期），再查幂等键；处理成功**之后**才 `markIdempotent` 写幂等键，业务失败不写、允许重试；`finally` 释放锁。

**优化细节**：
- Redisson 锁是**可重入**的，`isHeldByCurrentThread()` 判断后才 `unlock`，避免误删别人的锁。
- 幂等键"成功才标记"是关键优化：充值失败（余额没加上）不会留下幂等键阻断后续人工/自动重试；而支付宝重复回调因为首刷已标记，直接返回"已处理成功"，不重复加币。
- 打赏用"用户+小说+金额"做 5s 幂等，兼顾"防重复点击"和"允许间隔稍久的 legit 再次打赏"。

**解决什么问题**：从根上消除重复加币/重复打赏；即使支付网关重试、前端抖动也不产生资损。

## 五、高频面试问题（附回答要点）

1. **为什么不直接用本地缓存（Guava/Caffeine）？**
   多实例部署下本地缓存不共享，充值锁/幂等必须跨 JVM 一致 → 用 Redis 集中存储。本地缓存可叠加做进程内二级缓存（规划项）。

2. **缓存与 DB 一致性怎么保证？**
   Cache-Aside：写时删缓存、读时重建。接受极短脏读窗口；可升级"延迟双删"或订阅 binlog（Canal）异步删（规划）。

3. **缓存穿透/击穿/雪崩怎么防？**
   - 穿透：空值不缓存 + 后续可加布隆过滤器（项目目前靠 `disableCachingNullValues` + 参数校验，布隆是规划）。
   - 击穿：热点 key 失效时互斥重建/逻辑过期（规划）。
   - 雪崩：TTL 加随机抖动避免同时过期（当前固定 1h，可优化为 `1h + random`）。

4. **ZSet 底层是什么？为什么不用 MySQL 排？**
   跳表+哈希，范围/排名 O(logN)；MySQL `ORDER BY` 全表扫 O(N logN)，量大就慢。

5. **分布式锁你用什么？Redisson 锁特性？**
   Redisson RLock：可重入、自动续期（watch dog，默认 30s 续一次，防业务超时才释放）、支持红锁（多节点，更强一致但项目单机 Redis 用单节点锁）。

6. **锁超时但业务没执行完怎么办？**
   watch dog：只要客户端还持有锁且未主动释放，后台定时续期，不会提前过期；进程挂了续期停止，锁自然过期释放，避免死锁。

7. **怎么防止误删别人的锁？**
   释放前 `isHeldByCurrentThread()` 校验 value（Redisson 内部用线程标识）只删自己拿到的锁。

8. **为什么用 Redisson 而不手写 SET NX？**
   手写要自己处理续期、可重入、误删、集群；Redisson 用 Lua 脚本保证原子性，封装好续期与可重入，生产更稳。

9. **幂等为什么"成功才标记"，不是一开始标记？**
   一开始标记的话，业务失败（余额没加成功）会留下幂等键，阻断后续重试、造成"钱没到账但再也充不进"。成功才标记既防重复又允许失败重试。

10. **Redis 宕机，充值/打赏怎么办？**
    锁/幂等不可用 → 当前会抛"繁忙"或放行（我代码里幂等异常走保守放行，靠锁兜底）。生产应做降级：锁获取失败走本地限流/直接拒绝，并告警 + 人工对账。

11. **分布式锁能完全替代数据库唯一约束吗？**
    不能。锁是性能/并发层防御，DB 唯一索引（如订单号唯一）才是最终兜底，二者互补。

12. **热点小说（大 key）怎么处理？**
    阅读计数 ZSet 单 key 会随小说数增长；可按月/按日分片（`reads:202607`）再聚合，或限制 ZSet 长度（`ZREMRANGEBYRANK`）保留 top 段（规划）。

## 三、怎么设计的（编排与配置设计）

**1. 服务编排结构**（`docker-compose.yml`）：
- 基础设施层：mysql / redis / rabbitmq / elasticsearch / minio（+ 可选 kibana）
- 应用层：6 个微服务，全部用 `build:` 指向各自 `Dockerfile`，`image: tjnovel/xxx:local`
- 所有容器挂在**自定义 bridge 网络 `microservices-network`** 上，靠**服务名互相访问**（如 `jdbc:mysql://mysql:3306`、ES 用 `elasticsearch` 主机名），不用写死 IP——这是容器网络的核心好处。

**2. 配置外置（这是"开发/生产一致"的关键）**：
- 每个 `application.yml` 里所有连接信息都用 **`${ENV:default}` 占位符带默认值**：`spring.datasource.url: jdbc:mysql://${MYSQL_HOST:localhost}:3306/...`、`redis.host: ${REDIS_HOST:localhost}`、ES/MinIO/RabbitMQ 同理。
- **本地不跑 docker** 时，占位符走默认 `localhost`，直接连本机中间件，开发零配置；
- **跑 compose** 时，由 compose 的 `environment:` 注入真实地址（如 `mysql`、`elasticsearch` 容器名），启动时整体覆盖。
- 好处：同一份 jar、同一个配置模板，环境差异全部收敛到环境变量，**配置不写死在代码里**。

**3. 数据持久化**：mysql / redis / rabbitmq / elasticsearch / minio 各自挂**命名卷**（volumes），容器删了数据还在，重启不丢。

**4. 启动顺序控制**：每个中间件配 `healthcheck`（mysql 用 `mysqladmin ping`、redis 用 `redis-cli ping`、ES 用 `_cluster/health`、minio 用 `/minio/health/live`），微服务用 `depends_on: condition: service_healthy`——**中间件真正 ready 后微服务才启动**，避免"ES 还没起完，content-service 就连接失败"。

**5. 镜像构建**：后端 `Dockerfile` 用 `eclipse-temurin:17-jre`（只含运行时的轻量镜像），`COPY target/*.jar /app.jar` + `ENTRYPOINT java -jar`。前端有 `.env.development` / `.env.production` 区分构建时的 API 地址。

## 四、针对 ES 这种特殊中间件，在容器化时做了什么处理（回应"针对什么数据/怎么设计"）

ES 跟普通中间件不一样，我在 compose 里专门做了三件事：

- **`discovery.type=single-node`**：ES 默认要组集群，单节点必须显式声明"我是单节点"，否则一直卡在选主。
- **`ES_JAVA_OPTS=-Xms512m -Xmx512m`**：限制 JVM 堆内存。这是容器化 ES 最常见的坑——ES 默认会吃掉宿主机一半内存，不限制会拖垮整台机器。
- **`xpack.security.enabled=false` + 健康检查 + 数据卷**：开发阶段关掉鉴权方便联调，用 `_cluster/health` 探活、用卷持久化索引数据。

> 这套处理对应的就是"**针对有状态、启动慢、吃内存的中间件（ES），在容器化时单独配置内存上限、单节点模式、探活与持久化**"。

## 五、策略与优化细节

**策略：同一镜像 + 环境变量区分环境**（而不是"开发一套配置、生产一套配置"）。所有差异通过 `.env` 文件 / compose `environment` 注入，jar 包不变。

**优化细节**：
- **网络隔离**：自定义 bridge 网络，服务间用名字互通，天然隔离外部；只有真正需要暴露的端口（如 7080 网关、15672 RabbitMQ 管理台、9001 MinIO 控制台）才映射到宿主机。
- **配置松弛绑定**：compose 注入的是 `SPRING_DATASOURCE_URL`（全大写环境变量），Spring Boot 宽松绑定会自动映射到 `spring.datasource.url`，覆盖 yml 默认值——无需改代码即可切换环境。
- **密码不硬编码**：数据库/Redis/MinIO/RabbitMQ 的密码用 `${VAR:-默认值}` 从宿主环境变量读取，compose 里不放明文（生产用 `.env` 文件或密钥管理）。
- **健康检查分级**：中间件探活后才放行下游，避免竞态启动。

**解决了什么问题**：
- 环境一致性：新人 `docker compose up` 一条命令起全套，告别"我机器上能跑"。
- 配置漂移：连接信息收敛到环境变量，开发=生产同一份配置模板。
- 启动可靠性：健康检查 + 依赖顺序，避免中间件没 ready 导致服务连环失败。

## 二、项目亮点（挑 4 个讲，每个 = 做了什么 + 解决什么）

**亮点 1：Elasticsearch 全文检索替代 MySQL LIKE**
- 做了什么：小说元信息（书名/作者/简介）+ 章节正文建倒排索引，IK 中文分词，`bool` 查询里 `multiMatch` 对书名^3、作者^2、简介加权，章节搜索开原生高亮（`<em>` 不落盘）。

**亮点 2：Redis 三层应用——缓存 / 排行榜 / 分布式锁**

**亮点 3：大文本章节存储设计**
- 做了什么：正文用 `LONGTEXT` + `utf8mb4`，靠 InnoDB 行溢出存储（正文放溢出页、行内留指针），`wordCount` 冗余；正文只在读详情加载，搜索走 ES。
- 解决什么：单章几十 KB 不撑爆行、查短列不受正文影响；大文本检索交给 ES，不在 MySQL 做 `LIKE` 全表扫。

**亮点 4：容器化一键部署 + 配置外置**
- 做了什么：`docker-compose` 编排 6 服务 + 5 中间件，自定义网络服务名互通，`${ENV:default}` 占位符把连接信息全外置，健康检查控制启动顺序。
- 解决什么：新人一条命令起全套；开发/生产同一份镜像、配置靠环境变量区分，告别"环境漂移"。

## 三、技术难点与解决方案（讲 3-4 个真挑战）

**难点 1：检索与存储的数据一致性**
- 问题：章节既存 MySQL 又进 ES，怎么保证两边不偏？
- 方案：采用**同步双写**（发布/审核时直接调 `syncNovel/syncChapter` 写 ES），启动用 `@PostConstruct` 全量重建保基线；用 `@ConditionalOnProperty` 做开关——ES 没配就不启动同步、不影响主流程（优雅降级）。
- 进阶认知（被问可说）：双写非强一致，改进方向是改 MQ 异步解耦 + 定时对账补偿。

**难点 2：并发 + 重试双重风险下的资损防护**
- 问题：支付宝回调会重试、用户会重复点击，原代码无幂等会重复加币/扣币。
- 方案：**分布式锁（Redisson 可重入锁，解决并发同时到达的互斥）+ 幂等键（Redis SETNX，解决回调重试/重复点击的去重）** 双层防御；且幂等键"业务成功才标记"，失败不阻断重试。watch dog 防业务超时才释放锁、避免死锁。

**难点 3：跨服务数据一致性（打赏场景）**
- 问题：打赏要"扣读者币 + 加作者收入"，跨 transaction-service 和 user-service，没有分布式事务，任一步失败就资损或账目不平。
- 方案：transaction 内用本地事务保证"扣币 + 记交易 + 记作者收入"原子性，通过 WebClient 调 user-service 更新作者收益；查询类用最终一致性（MQ/异步）。锁+幂等保证同笔打赏不重入。
- 诚实点：当前是**本地事务 + 跨服务调用**，没上 Seata/TCC 这类分布式事务框架，极端情况下靠对账补偿（规划）。

**难点 4：大文本高性能读写**
- 问题：章节正文几 MB，直接 SELECT * 或 LIKE 会拖垮 DB。
- 方案：LONGTEXT 行溢出让短列查询不受正文大小影响；列表/搜索接口不 SELECT content；字数冗余字段避免扫文本；检索职责完全交给 ES。
